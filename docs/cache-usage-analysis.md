## 집계와 해석

- 로컬 Codex 세션 JSONL에서 측정 구간과 주담당 세션을 고른다. `token_usage_record`의 `response_id` 중복을 제거하고 `usage` 값을 합산한다. 구간은 시작·종료 이벤트나 사용자 요청 시각으로 기록한다. 원문이 필요할 때 참고할 로그 위치는 [기존 인계문](CACHE_HANDOFF.md#토큰-집계-방법과-정정)에 있다.
- 비캐시 입력은 `input_tokens - cached_input_tokens`다. 출력은 추론 토큰을 포함한 `output_tokens`다. 합계는 캐시 입력, 비캐시 입력, 출력을 한 번씩 더한 값이다.
- 캐시 입력은 모델이 여러 요청에서 재사용한 문맥의 누계다. OpenAI 서버는 동일한 프롬프트 앞부분의 내부 계산 결과인 KV 상태를 재사용한다. 저장소의 실제 전송 범위는 별도 기록으로 확인한다. 캐시에는 할인 요율이 적용되며, 로그의 원시 토큰 수와 구독 한도·크레딧 차감량은 별도로 확인한다. [프롬프트 캐싱](https://developers.openai.com/api/docs/guides/prompt-caching) · [Codex 토큰 요율](https://learn.chatgpt.com/docs/pricing#token-rates)
- #7의 비캐시 입력과 출력 합계는 316,336개다. 다른 사람의 미션 전체 사용량과 비교하려면 집계 방식, 모델, 추론 강도, 보조 에이전트 포함 범위를 맞춘다.
- #7의 macOS CI 자체는 18초였다. 승인부터 다음 요청까지의 구간에는 Git 인증 대기·재시도, 조회·보고, 모델 응답이 포함됐다. 각 절차의 시간·토큰 기여도는 따로 측정하지 않았다. [macOS CI 기록](https://github.com/ntt65/A4_2/actions/runs/43620638944)

```json
{"input_tokens":19701,"cached_input_tokens":13696,"cache_write_input_tokens":0,"output_tokens":18,"reasoning_output_tokens":11}
```

이 이벤트 기준 비캐시 입력은 `6005`, 입력과 출력의 합계는 `19719`다. 사전 점검은 `--ephemeral`로 실행했으며, 비교 실행에서는 원문 JSONL과 세션 로그를 보관할 수집 경로를 준비한다. 실제 모델·추론 강도와 개별 응답 수를 사용량 이벤트만으로 확인할 수 있는지는 미확인이다.

### 비교 조건

분산 구성 A는 `0f03aeca843d3350f172f91fbd19c073f462e752`의 루트·`src/`·`docs/` 지침 3개다. 통합 지침 원본은 `894e9ae`다. 코드·문서를 동일하게 유지하기 위해 측정 전용 스냅샷 `26efe80`을 만들었으며, 기준 `0f03aec`과의 차이는 지침 3개 경로뿐이다. 이 스냅샷의 루트 지침은 `894e9ae`와 바이트 단위로 일치한다. 한 작업 트리에서 두 커밋을 전환해 양쪽 모두 깨끗한 Git 상태로 실행했다. 각 지침과 동일하게 고정한 파일의 SHA-256을 `manifest.json`에 기록했다.

각 실행은 저장소 루트에서 독립 새 세션으로 시작한다. 모델 `gpt-6.1-sol`, 추론 강도 `ultra`, 클라이언트 버전, 전역 지침, 프롬프트, 도구·권한, 출력 형식을 고정한다. IDE 문맥과 보조 에이전트는 양쪽 모두 사용하지 않는다. 명령행 인자와 실제 세션의 모델·추론 강도·작업 경로·적용 지침을 대조하고, 일치 여부를 원자료에 남긴다. 전역·프로젝트 설정을 바꿔야 하는 경우에는 영향과 승인 범위를 먼저 확인한다.

### 고정 과제와 정답

최초 계획의 3과제는 다음과 같다. 이번 총 3회 제한 실험은 코드 조회 과제만 실행했다. 각 프롬프트 앞에 다음 공통 지시를 그대로 붙인다.

```text
읽기 전용으로 작업하고 관련 AGENTS 지침을 확인하라. 파일 수정과 보조 에이전트 사용 없이 요청한 파일의 근거를 확인하라. 최종 답변은 요청한 키만 가진 JSON 객체로 반환하라.
```

| 과제 | 공통 지시 뒤에 붙일 프롬프트 | 기준 파일에서 확인한 정답 |
| --- | --- | --- |
| 코드 조회 | src/extractor.py에서 한글 단위 금액을 정규화하는 함수의 이름과 정의 행 번호를 찾고, tests/test_extractor.py에서 '1억 2천만원'을 검사하는 test_at_least_three_variants_per_pattern의 기대 금액을 확인하라. 키는 function, line, expected_amount다. | `_normalize_korean_amount`, `118`, `120000000` |
| 문서 조회 | docs/devops.md의 환경 계약에서 프로젝트 Python 버전, uv 버전, 평가 OS, 테스트 러너를 확인하라. 키는 python, uv, evaluation_os, test_runner다. | `3.11`, `0.13.7`, `macOS`, `unittest` |
| 코드·문서 조회 | main.py와 docs/extraction.md를 대조해 --mask 사용 시 원문 정보 추출과 분석 문장 마스킹의 순서를 확인하라. 키는 first_call, second_call, documented_order다. documented_order에는 문서와 코드가 일치하면 extract_then_mask를 넣어라. | `extract_information`, `mask_personal_info`, `extract_then_mask` |

코드 조회는 `function` 문자열, `line`·`expected_amount` 정수로 판정한다. 나머지 과제의 값은 문자열이다. JSON 파싱과 모든 키·값 일치를 검사하며, 설명이나 마크다운이 섞인 답변도 형식 실패로 기록한다. 실행 준비 시 기준 파일과 정답을 다시 대조한다.

### 실행 순서와 집계

최초 계획은 3과제 × 2구성 × 3반복의 18회였다. 아래 표는 최초 계획이며 실제 실행은 위의 총 3회 시도 표와 같다. 같은 작업 경로에서 A 또는 B 커밋으로 전환해 경로 차이를 통제하고 실행 전후 코드·테스트·조회 문서 해시를 확인했다. 실행 간 대화 이력은 공유하지 않았다.

| 쌍 번호 | 과제 | 반복 | 실행 순서 |
| --- | --- | ---: | --- |
| 1 | 코드 조회 | 1 | A → B |
| 2 | 문서 조회 | 1 | B → A |
| 3 | 코드·문서 조회 | 1 | A → B |
| 4 | 코드 조회 | 2 | B → A |
| 5 | 문서 조회 | 2 | A → B |
| 6 | 코드·문서 조회 | 2 | B → A |
| 7 | 코드 조회 | 3 | A → B |
| 8 | 문서 조회 | 3 | B → A |
| 9 | 코드·문서 조회 | 3 | A → B |

각 실행의 시작·종료 UTC 시각과 단조 시계 경과 시간을 기록한다. 시간 범위는 CLI 프로세스 시작부터 최종 응답을 포함한 프로세스 종료까지로 맞추고, 모델·도구·대기 시간을 포함한다. 종료 코드, 세션 ID, 원문 최종 답변, 정답 일치 여부, 모델 응답 수, 도구 호출 수, 고유 응답별 입력·캐시 입력·출력 토큰을 남긴다. `response_id` 중복을 제거해 합산하고 비캐시 입력은 입력에서 캐시 입력을 뺀다. 출력·추론의 중복 합산을 피한다. CLI와 세션 로그의 필드가 다르면 실제 스키마와 집계 경로를 먼저 기록한다.

캐시 입력, 비캐시 입력, 출력, 전체 토큰과 경과 시간은 각각 비교한다. 과제별 3개 실행값, 중앙값, 같은 쌍의 B−A 차이와 증감률을 함께 제시한다. 기준값이 0이면 증감률은 계산 불가로 표시한다. 파일 바이트 수는 보조 정보로만 기록한다. 실패와 재시도는 원래 실행 기록에 남기고, 재시도 값을 원래 값과 바꿔 넣지 않는다.

### 결과 판정

두 구성의 정답 통과율을 먼저 확인한다. 같은 쌍의 A·B가 모두 정답을 통과한 실행에서 토큰 항목과 시간을 비교하고 실패 실행의 비용도 별도 표에 보존한다. 과제별로 방향이 다르거나 변동 폭이 크면 그 결과를 그대로 기록한다. 캐시 상태와 서버 지연은 완전히 통제했는지 확인할 수 없으므로 실행 순서·캐시 사용량과 함께 해석한다. 이번 한 쌍에서는 전체 토큰 25.44% 감소와 경과 시간 3.52% 증가를 관측했다.

## 후속 검증

1. 비교를 반복할 때 실험 전 긴 이력을 재현하고 실행 순서를 교대한다. 모델과 추론 강도는 실행 쌍마다 고정하고, 강도별 효과는 별도 실험으로 잰다.
2. `rg`와 SQLite는 채팅 조건과 작업을 고정해 비교한다. SQLite 제안은 파일·심벌·테스트·문서 위치와 승인·검증 기록에서 필요한 행을 반환하는 방식이다. 인덱스 구축과 조회 시간은 각각 기록한다.
3. 독립 커밋별 채팅 운영은 [공통 지침의 토큰 사용량 관리](../AGENTS.md#토큰-사용량-관리)를 따른다. 접근 범위는 샌드박스와 연결 도구 권한으로 적용한다. 변경 파일이 겹치는 작업의 순서와 최종 회귀 검증은 VS Code 주담당이 관리한다.
