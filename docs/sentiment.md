# 감성 사전·규칙·고정 평가 데이터

이슈 #4는 기존 함수의 입력·출력 계약을 유지하면서 대소문자, 한국어 표면형,
부정 범위, 강조어와 이중부정을 보완한다. 정보 추출·CI 설정은 변경하지 않는다.

## 사전 구축과 출처

외부 사전이나 웹 자료를 다운로드하지 않았다. 기존 프로젝트의 자체 목록을
검토하고 교육용 한국어 표현을 수작업으로 보완했다. 기존 메타데이터에 있던
국립국어원 관찰 목록이라는 주장은 확인 근거가 없어 활성 사전에서 삭제했다.
국립국어원 출처 또는 외부 라이선스가 확인되었다고 주장하지 않는다.
프로젝트 내부 작성 자료이며 별도의 외부 라이선스 검증은 수행하지 않았다.

- 일반 어휘 207개: 긍정 106개, 부정 101개.
- 도메인 어휘 36개: 구매·배송·결제·문의·AS 표현.
- 의미 없는 `긍정확장1` 등 12개를 실제 어휘로 교체하고 기본 어휘 7개를 보완했다.
- `surface_forms`는 불규칙 활용의 명시적인 별칭이다. 형태소 분석기나 학습 모델이 아니다.
- 사전 키와 입력 토큰을 모두 `casefold()`하여 `AS만족`, `as만족`, `AS불만`을 처리한다.

원본 두 JSON은 `data/archive/`에 바이트 그대로 보존했다. 원본의 확인되지 않은
출처 설명도 역사 자료로 보관할 뿐, 현재 사전의 출처 근거로 사용하지 않는다.
원본 작업 폴더는 Windows의 CRLF 개행이었다. archive는 Git의 자동 LF 정규화를
적용하지 않고 이 바이트를 보존한다. 기준 커밋의 Git blob과는 개행만 다르며
LF로 정규화한 내용은 같다.
스테이징은 archive 두 파일에 한해 `git -c core.autocrlf=false add -- ...`를 사용한다.
원본 CRLF의 CR을 공백으로 경고하는 기본 검사와 구분하여, archive 외 파일은 일반
`git diff --cached --check`로, 전체는 `git -c core.whitespace=cr-at-eol diff --cached --check`로 검사한다.
이 옵션은 해당 명령에만 적용하며 저장소·시스템 설정을 변경하지 않는다.

| 보존 파일 | 원본 SHA-256 |
|---|---|
| `data/archive/sentiment_lexicon.json` | `76ebcd0528283684aad787efc0f7fe9ccd1c8213ffc5c51cc4bb1176094b7184` |
| `data/archive/sentiment_test_cases.json` | `fb2da83c6f55b6d04ad4355a05d854df10d26bc69b461ca521449802ff48a2ef` |

## 규칙과 반환 계약

`analyze_sentiment(text, lexicon=None, use_rules=True)`와 `format_analysis(result)`를 유지한다.
반환 키는 `text`, `tokens`, `detected_sentiments`, `rule_logs`, `final_score`, `label`이다.
각 매칭은 `token`, `base_score`, `weight`, `weighted_score`, `rules`를 반환한다.
이중부정도 매칭 근거를 반환하며 소비한 토큰을 다시 합산하지 않는다.
명시적으로 전달한 빈 사전 `{}`는 기본 사전으로 대체하지 않는다.

1. 내장 `re`로 한글·영문·숫자의 최대 연속 구간을 토큰화한다. 단어 전체를 비교하여
   `불친절하다`에 포함된 `친절하다`가 긍정으로 부분 매칭되지 않도록 한다.
2. `다`형 표제어의 제한된 어미, `하다`의 `해요/했어요` 활용, 명시적 별칭을 비교한다.
   `좋지 않다`, `맛있지 않았어요`, `친절하지 않아요`를 지원한다.
3. 앞쪽 최대 세 토큰의 연속된 부정어·강조어·허용 부사를 처리한다. 뒤쪽도
   인접한 부정 보조 용언(`않다/없다/아니다`)과 허용 부사만 검사한다. 접두 부정어
   `안/못`을 앞 감성어에 적용하지 않으므로 `좋고 안 나쁘다`는 긍정이다. 다른 명사나 감성어를 넘어가지 않는다.
4. 문장부호·줄바꿈·접속어와 `지만/는데` 경계로 수식 범위를 제한한다.
   `좋다. 문제는 없다`의 첫 감성은 뒤집지 않는다.
5. 부정은 점수에 `-1`, 강조는 `1.5`를 곱한다. 반복 강조어는 강도를 무한히 키우지 않는다.
6. 사전에 등록한 `나쁘지 않다`, `싫지 않다`, `불편하지 않다`는 긍정 보정한다.
   `않아요/않았어요` 및 `지는/지도` 변형을 지원한다.

`use_rules=False`도 동일한 대소문자·표면형 매칭을 사용하지만 부정 반전·강조·이중부정은
적용하지 않는다. 따라서 아래 전후 비교는 동일한 개선 사전에서 규칙 효과를 비교한 것이다.

## 평가 데이터의 작성·고정

새 `data/sentiment_test_cases.json`은 160개 문장, 고유 문장 160개다.
숫자만 바꾸거나 동일 문장을 복제하지 않았다. 긍정 55개, 부정 70개, 중립 35개다.
기존 116행·고유 31문장은 archive에 보관한다.

| 유형 | 문장 수 |
|---|---:|
| 일반 감성 | 40 |
| 표면형 | 20 |
| 사실·중립 | 25 |
| 부정·이중부정 | 15 |
| 강조 | 10 |
| 도메인 | 20 |
| 반어 | 10 |
| 인용·단어 언급 | 6 |
| 문맥·최종 의사 | 10 |
| 복합 감성 | 4 |

라벨 기준은 작성 시 고정했다. 명시적 만족·재구매 의사는 긍정, 불만·거절·서비스 실패의
반어는 부정, 사실 전달·단어 자체를 인용한 예문은 중립으로 보았다. 복합 감성 중 전체
판정을 명시하지 않은 네 문장은 이 데이터의 표기 규약에 따라 중립으로 두었다.
이 규약은 측면별 감성을 표현하는 정답 체계를 대신하지 않는다.
도메인 일부는 리뷰 태그처럼 붙여 쓴 표현을 포함한다.

문장과 라벨을 JSON에 작성한 다음 아래 작성 환경의 SHA-256을 출력하고, 그 뒤 모델을 처음 실행했다.
예측 결과를 확인한 뒤 문장·라벨을 변경하지 않았다.

- 작성 환경의 CRLF 바이트: `995eb848614476b8a6846660584abe5631a8c5d395876a0c8a7c63970c1bc806`
- LF 개행으로 정규화한 바이트: `bf417f66b571c779792ef1784d4a1f93b9f6893eeb8881a4257f09f962bb0816`

새 평가 JSON은 일반 텍스트 파일이므로 checkout 환경에 따라 CRLF/LF가 달라질 수 있다.
플랫폼을 넘나드는 데이터 대조에는 LF 정규화 해시를 사용한다.

이 자료는 수작업 개발용 점검셋이다. 독립된 평가자나 블라인드 평가·분리된 검증셋을
사용하지 않았으므로 실제 고객 데이터의 일반화 성능으로 해석하면 안 된다.

## 검증 범위와 남은 한계

신규 테스트는 표면형, AS 대소문자, 전체 단어 경계, 절별 부정 범위, 실제 가중 점수,

## Aspect별 감성 분석

`src/aspect_sentiment.py`의 `analyze_aspects(text, lexicon=None, use_rules=True)`는 아래 명시적 측면을 구분한다. 새 정규식·외부 라이브러리를 추가하지 않고 기존 내장 `re` 토큰·절 경계와 감성 분석기를 사용한다. 기존 `analyze_sentiment`의 반환 키·점수 규칙과 문장 평가 160개는 유지한다.

| 표준 측면 | 명사·별칭 |
| --- | --- |
| 음식 | 음식, 맛, 요리, 메뉴 |
| 가격 | 가격, 비용, 요금, 가성비 |
| 서비스 | 서비스, 응대, 상담, 직원 |
| 배송 | 배송, 배달, 택배 |
| 품질 | 품질, 성능, 내구성 |

명사 전체 또는 허용 조사와 결합한 토큰을 사용한다. `맛있다`, `음식점`, `가격표`, `서비스업`, `배송지`는 측면 명사로 부분 매칭하지 않는다. 문장부호·줄바꿈·접속어·`지만/는데`로 절을 나누고, 각 절의 측면 명사부터 다음 측면/절 경계까지 기존 감성 규칙을 적용한다. 앞쪽 감성어와 생략·대명사의 측면은 추론하지 않는다. 미등록 주어는 경계로 인식하지 못하므로 감성을 앞의 지원 측면에 잘못 합산할 수 있다.

`음식과 서비스가 좋다`, `배송 및 품질이 안 좋다`처럼 조사 `과/와/랑/이랑/하고` 또는 연결어 `및/그리고`로 명시한 나열에는 공유 술어를 적용한다. 쉼표는 절 경계이므로 공유하지 않는다. 같은 표준 측면의 서로 다른 구간 점수는 합산하며 `>0.5`는 긍정, `<−0.5`는 부정, 그 사이는 중립이다. `음식은 좋다. 메뉴는 나쁘다`는 0점·중립이다. 동일 구간의 `음식과 메뉴`는 같은 측면으로 한 번만 합산한다. 상쇄된 중립은 문맥상 감성이 없다는 의미와 구별해 토큰 근거를 확인해야 한다.

반환 루트는 `text`, `aspects`다. `aspects`는 등장 순서의 목록이며 각 항목은 `aspect`, `mentions`, `segments`, `detected_sentiments`, `final_score`, `label`을 갖는다. `mentions`는 명사·조사의 원문과 `[start, end)` 문자 구간이다. `segments`에는 분석한 원문·구간, 감성 근거·규칙 로그·점수·판정이 들어 있다. 측면의 `detected_sentiments`는 매칭 `token`, `base_score`, `weight`, `weighted_score`, `rules`와 해당 원문 `segment_span`을 반환한다. 지원 명사가 없으면 `aspects=[]`, 명사가 있고 감성 근거가 없으면 0점·중립이다. `use_rules=False`와 명시적 빈 사전 `{}`도 지원한다.

### 실제 실패 6문장

아래는 전체 36문장 중 완전 일치하지 않은 모든 문장이다. `+`, `−`, `0`은 각각 긍정·부정·중립이며 `{}`는 측면 미탐이다.

- [맛있지만 비싸다] → [음식+, 가격−] vs [{}] → 명시적 측면 명사가 없어 음식·가격을 추론하지 못한다.
- [배송은 빠르다. 그것은 느리다] → [배송0] vs [배송+] → 대명사 `그것`을 배송에 연결하지 않아 후속 부정 감성을 합산하지 못한다.
- [음식, 서비스가 좋다] → [음식+, 서비스+] vs [음식0, 서비스+] → 쉼표가 절 경계라서 공유 술어를 음식에 연결하지 못한다.
- [맛있는 음식과 친절한 서비스] → [음식+, 서비스+] vs [음식+, 서비스0] → 명사 앞의 관형어를 해당 측면에 연결하지 못한다. 음식의 긍정도 `맛있는`이 아니라 뒤에 놓인 `친절한`을 잘못 연결한 결과다.
- [서비스는 참 친절하다, 두 시간을 기다리게 하다니] → [서비스−] vs [서비스+] → 앞 절의 긍정 어휘를 반어로 해석하지 못한다.
- [음식은 좋고 주차는 나쁘다] → [음식+] vs [음식0] → 미등록 주어 `주차는`을 측면 경계로 인식하지 못해 부정 술어를 음식에 합산한다.

### 실행과 검증

```shell
uv run --python .venv python -B -X utf8 main.py --text "음식은 맛있는데 가격이 비싸요" --aspect
uv run --python .venv python -B -X utf8 main.py --evaluate-aspect
```

`--aspect`는 `--text`를 필요로 하며 기존 분석 뒤에 측면 결과를 출력한다. `--mask`와 함께 사용하면 마스킹된 표시 문장을 분석한다. `--evaluate-all`은 기존 정보 추출·문장 감성 평가이며 측면 평가는 `--evaluate-aspect`로 별도 실행한다.

신규 테스트 18개를 포함한 전체 69개를 3.254초에 실행해 68개가 통과했다. 실패 1개는 `불편하지 않다`의 기존 사전 점수 1.2를 테스트가 1.5로 가정한 기대값 오류였다. 해당 기대값 수정 후 관련 15개 테스트가 0.114초에 모두 통과했다. 나머지 54개는 최초 실행에서 통과했고 이후 관련 소스 변경이 없다. 미션 예시, 부정·강조·이중부정의 근거, 측면/절 경계, 별칭·부분 단어 배제, 공유 술어, 반복 상쇄·별칭 중복 합산 방지, 원문 구간, 빈 사전·규칙 끄기·빈 자료, 누락·오탐 지표 계산, CLI 옵션 의존성·마스킹·저장소 밖 실행을 검증했다.
